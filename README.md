# goal

The goal is to automatically maintain a publicly recognized SSL certificate.  The recommended client is `certbot`, implementing the `ACME` protocol.  Refer to [letsencrypt.org](https://letsencrypt.org).

# certbot user account

The default of both upstream and debian packaged certbot seems to be to run `certbot` as root.  I find that distasteful, so I am creating a `certbot` user and adjusting various permissions.  This will mean that the `--standalone` mode of operation is unavailable, as `certbot` cannot bind port 80, but the plan is to integrate with `nginx`.

# opinion on delegation

I would prefer to operate my own certificate authority, and I do, but it will not be recognized by strangers.  I would like to have authority for my domain delegated to my CA, but my current understanding is that this possibility has been ignored by typical implementations of `SSL`/`TLS`/`X.509`, and instead they recognize any valid CA as authoritative for all domains, so that a CA cannot delegate authority over my domain without delegating authority over *all* domains.  Even I don't want that, and neither do recognized CAs, so instead of getting my CA certs signed, I need to acquire site certificates or certificate signatures from a recognized CA.

# integration with nginx role

Using the certificate generated by `certbot` for `nginx` will require some further thought.  The `nginx` role might depend on `letsencrypt-client` to have certificates available, but `letsencrypt-client` might also depend on `nginx` to obtain the certificates.  The probably solution will be some conditional logic in the `nginx` role to refer to certificates obtained by `certbot` if available and otherwise refer to default certificates signed by my (not publicly recognized) CA.  The first use case is for mail, so this issue can be avoided for now.
